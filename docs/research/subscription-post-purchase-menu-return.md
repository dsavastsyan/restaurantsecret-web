# Post-purchase flow: возврат в меню после подписки

**Дата исследования:** 2026-10-03<br>
**Продукт:** `restaurantsecret-web`<br>
**Статус:** UX-исследование и рекомендация для продуктового решения; код не изменён.

## Короткий вывод

Для пользователя, который начал оформление из конкретного меню, лучший основной
сценарий — после подтверждённой активации вернуть его в то же меню и показать там
ненавязчивое подтверждение, что premium-доступ открыт.

Рекомендуемый MVP:

1. сохранить исходный menu URL, scroll position и, если был открыт modal блюда, его
   идентификатор;
2. после возврата от платёжного провайдера дождаться подтверждения entitlement через
   API/webhook, а не считать сам redirect доказательством активации;
3. после `active` перейти обратно в меню;
4. поверх меню показать один success-banner/modal с коротким сообщением и действием
   `Продолжить просмотр`;
5. если активация ещё не подтверждена, оставить пользователя на промежуточном
   экране/состоянии `Проверяем доступ…`, с автоматической повторной проверкой и
   понятным fallback.

Не рекомендуется оставлять пользователя на общей странице подписки или отправлять
его на главную: это ломает исходное намерение и заставляет заново искать ресторан.

## Текущая реализация

В меню CTA сохраняет `returnTo` и ведёт гостя на OTP-логин:

- `src/components/DishCard/DishCard.tsx` передаёт `{ from: "/account/subscription", returnTo }`;
- `src/components/MenuRedesign/DishTileV2.tsx` использует тот же контракт;
- `src/pages/Login.tsx` после входа отправляет пользователя в `/account/subscription`,
  если активной подписки ещё нет.

После этого исходное меню фактически не используется для post-payment redirect. В
пробном flow `src/pages/account/Subscription.tsx` передаёт YooKassa
`return_url = /account/subscription`, а сам `Subscription`-экран опрашивает backend
для активации trial. Варианты `/pay/success` и `/pay/result` также предлагают перейти
в аккаунт, а не восстановить исходный menu context.

Дополнительный технический риск: `src/app/AppShell.jsx` при смене pathname/search
принудительно скроллит страницу в начало. Поэтому одного сохранения URL недостаточно
для возврата «на тот же экран».

## Что проверено в источниках

### 1. Контекст важнее лишнего промежуточного экрана

Apple HIG рекомендует давать пользователю прямой путь к нужной задаче, сохранять
контроль и размещать status feedback рядом с объектом, которого он касается. Для
важного завершившегося действия подтверждение уместно, но оно должно соответствовать
значимости события. Это поддерживает возврат в исходное меню с локальным feedback, а
не обязательное перенаправление на отдельную «спасибо»-страницу.

Источники: [Apple HIG — Design principles](https://developer.apple.com/design/human-interface-guidelines/design-principles),
[Apple HIG — Feedback](https://developer.apple.com/design/human-interface-guidelines/feedback?changes=latest_5_9),
[Apple HIG — Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts?changes=_1).

### 2. Подтверждение должно быть явным, но не мешать продолжению задачи

Material Design описывает snackbar как краткое, ненавязчивое сообщение о уже
произошедшем действии с одной опциональной action-кнопкой; он не должен быть
единственным местом для важного сообщения. Apple отдельно предупреждает, что alert
прерывает текущий контекст и должен использоваться только для критичной или
actionable-информации.

Следствие для RestSecret: использовать banner/toast или компактный success-sheet,
но не блокирующий popup с единственной кнопкой `OK`. Для платежа полезнее показать
результат и сразу вернуть пользователя к блюду/меню.

Источники: [Material Design — Snackbars](https://m2.material.io/components/snackbars),
[Material 3 — Snackbar API guidance](https://developer.android.com/reference/kotlin/androidx/compose/material3/Snackbar.composable),
[Apple HIG — Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts?changes=_1).

### 3. Redirect после оплаты не равен подтверждённой активации

Официальная документация YooKassa описывает `return_url` как место возврата
плательщика и рекомендует на этой странице запрашивать актуальный статус платежа.
Статус может измениться асинхронно; для отслеживания изменений предназначены
webhook-события вроде `payment.succeeded`. Stripe формулирует тот же архитектурный
принцип: выдачу доступа/fulfillment нельзя строить только на success redirect,
потому что пользователь может не вернуться на страницу.

Следствие: сначала backend должен подтвердить `active`, затем frontend возвращает
пользователя в меню и показывает «доступ открыт». Если статус ещё `pending`, нельзя
показывать окончательное «всё готово».

Источники: [ЮKassa — входящие уведомления](https://yookassa.ru/developers/using-api/webhooks),
[ЮKassa — рекомендации по `return_url`](https://github.com/yoomoney/yookassa-github-docs/blob/master/checkout-api/031-02%20return_url.md),
[Stripe — fulfillment and webhooks](https://github.com/stripe/ai/blob/main/skills/stripe-best-practices/references/payments.md).

### 4. Confirmation screen не должна быть тупиком

Baymard отмечает, что confirmation step должен явно подтверждать покупку и основные
детали, но также может давать полезные следующие действия и продолжение сценария.
Для RestSecret таким следующим действием является не общий аккаунт, а возвращение к
тому меню, ради которого пользователь купил доступ.

Источник: [Baymard — 6 ways to improve the order confirmation page](https://baymard.com/research-articles/order-confirmation-page).

## Рекомендуемый UX flow

### Сценарий с подтверждённой активацией

1. Пользователь открывает `/restaurants/:slug/menu` и нажимает `Попробовать бесплатно`.
2. В session-scoped checkout context сохраняются:
   - `returnPath` — полный menu URL с query;
   - `scrollY`;
   - `restaurantSlug`;
   - `dishId`, если CTA был внутри открытой карточки блюда.
3. После OTP и optional onboarding пользователь идёт на страницу подписки.
4. После возврата от YooKassa приложение синхронизирует trial/payment status.
5. Когда API возвращает `active`, приложение переходит к сохранённому menu URL.
6. После восстановления scroll/modal показывает success state.

### Текст success state

Предлагаемый вариант:

> **Готово — premium-доступ открыт**<br>
> Теперь доступны КБЖУ и состав всех блюд.

Кнопка: **Продолжить просмотр**.<br>
Вторичное действие: **Управлять подпиской**.

Если пользователь вернулся именно к блюду, можно уточнить:

> **Теперь можно посмотреть это блюдо полностью**

Не стоит писать только «Спасибо за оформление»: это подтверждает эмоцию, но не
объясняет, что изменилось и что делать дальше. Не стоит также обещать «все
возможности сервиса», если часть возможностей зависит от другого состояния или
будет доступна только после отдельного шага.

### Состояние задержки активации

Если платёж прошёл у провайдера, но entitlement ещё не синхронизирован:

> **Платёж получен — проверяем доступ**<br>
> Обычно это занимает несколько секунд. Мы автоматически обновим статус.

Действия: `Проверить ещё раз`, `Вернуться в меню`. При возврате в меню premium
карточки должны оставаться в состоянии `проверяем`, пока API не подтвердит доступ.

### Ошибка или отмена

Не возвращать пользователя молча в меню. Показать:

> **Не удалось подтвердить подписку**<br>
> Деньги не списываются повторно автоматически. Проверьте статус или попробуйте ещё раз.

Действия: `Проверить статус`, `Повторить оформление`, `В меню`.

## Почему не делать обязательный modal

Полноэкранный modal после оплаты допустим, если он нужен для критичного результата,
но в этом сценарии он создаёт второй барьер сразу после уже пройденного checkout.
Пользователь пришёл не за «праздничным экраном», а за конкретным блюдом. Поэтому
лучше:

- desktop: компактный success-banner в контексте меню;
- mobile: bottom sheet или toast с action, который не закрывает меню;
- modal использовать только при pending/error, когда пользователю действительно нужно
  сообщить состояние и предложить действие.

## Что нужно изменить технически

1. Ввести единый `postCheckoutContext` в `sessionStorage` с TTL и безопасной проверкой
   same-origin path.
2. Перед переходом из menu в login сохранить `pathname + search`, `scrollY` и открытое
   блюдо.
3. Передавать `return_url` для обычного `/api/payments/create` так же явно, как уже
   делается для trial attach; лучше использовать отдельный callback route с payment
   context, а не полагаться на глобальный env default.
4. После возврата сначала синхронизировать entitlement, затем восстанавливать меню.
5. На меню восстановить scroll после загрузки данных; для открытого блюда повторно
   открыть modal только если dish всё ещё существует и доступен.
6. Сделать fallback на `/account/subscription`, если context истёк, URL невалиден,
   меню удалено или пользователь открыл checkout напрямую.
7. Не выдавать premium-доступ на основании только query-параметра `success` или
   факта возврата с YooKassa.

## Измерение и эксперимент

События:

- `checkout_started` с `source_menu_path`;
- `checkout_returned` с `return_context_available`;
- `subscription_activated`;
- `post_purchase_menu_restored`;
- `post_purchase_success_feedback_shown`;
- `post_purchase_continue_clicked`;
- `post_purchase_pending` / `post_purchase_failed`.

Первый эксперимент:

- **A:** возврат в то же меню + компактный success-banner;
- **B:** текущая страница `/account/subscription` + CTA «Открыть меню».

Основная метрика — доля пользователей, которые после подтверждённой активации
открыли premium-блюдо в течение сессии. Guardrails — ошибки восстановления context,
повторные переходы в checkout, `pending` дольше 30 секунд и обращения в поддержку.

Количественный uplift заранее не предполагается: текущих данных недостаточно, чтобы
оценить эффект до запуска A/B или staged rollout.

## Итоговая продуктовая рекомендация

Зафиксировать целевой сценарий как **«оплата → тот же ресторан/то же меню → доступ
к закрытому блюду»**. Success-feedback нужен, но должен быть коротким, конкретным и
не вытеснять меню. Для MVP достаточно banner/toast с action и корректного восстановления
context; отдельный красивый thank-you modal имеет смысл тестировать позже, если
аналитика покажет, что пользователи не замечают открывшийся доступ.
